Market Data & Analysis Architecture

marketdata · analysis · strategy: data flow, scheduling, triggers and communication (REST-only, v1)

Scope. How market data is collected from the exchange (Nobitex, REST API), stored in PostgreSQL, and handed to the analysis and strategy modules; which component triggers what; how backfilling, live updates and derived timeframes are scheduled.

Out of scope for now. WebSocket (later: live price feed only), Kafka/Flink, agents (only the hooks they will need), order execution.

2. Guiding conclusions

  • PostgreSQL is the source of truth for candles. Events are a "wake-up call that also carries the data", never the truth.
  • One scheduler, in marketdata. Analysis and strategy are purely event-driven; they never poll.
  • REST only for storing candles. REST candles are final; WebSocket snapshots can miss the last seconds of a candle (observed in a test). WebSocket comes back later as a live price feed (stops, paper fills), not as a candle source.
  • No Kafka/Flink now. Volume is a few thousand candles per day. Events go through a publisher interface: in-process now, Kafka with a transactional outbox later, without changing producers or consumers.
  • Closed candles only are stored and published. Decisions are made only on closed candles.
  • Library modules never read env/config files; callers pass config objects in (later: Spring Boot modules).
  • Collect broadly, derive on demand: collection is per coin and continuous; timeframes are cheap derived views created when someone subscribes.

3.2 Resolutions: what is collected vs derived

PeriodStored resolutionHow
2018 → 7 days agonative H1one-time deep backfill (~140 calls per coin)

Why M5 as base: M1 is not needed by any planned strategy (fees and spread dominate at that scale); M5 gives 12 slices per hour for realistic backtests (stop vs. take-profit order inside an H1 candle) and still derives M15/M30. Coarser later is always possible, finer never (7-day limit). The base resolution is per-exchange config, not hard-coded.

3.3 Aggregation rule (verified against Nobitex)

Test (BTCUSDT, 7 complete hours): aggregating M1 while skipping v=0 filler candles reproduced Nobitex's native H1 exactly (OHLCV). Naive aggregation got the open wrong. Aggregating M5 gave exact OHLC; volume differed by ~1e-8 (M5 volume is rounded to 8 decimals).

derive(bucket):                         // e.g. one H1 bucket from its M5 candles
  traded = candles in bucket with volume > 0
  if traded is empty:
      return flat candle (o=h=l=c = previous close, v = 0)   // same as the exchange
  open   = traded.first.open
  high   = max(traded.high)
  low    = min(traded.low)
  close  = traded.last.close
  volume = sum(all candles.volume)
  // compare with native candles using a small volume tolerance, not exact equality

3.4 Collected universe vs subscribed series

  • Collected universe (marketdata config): ideally all USDT pairs. Passive collection needs ~1 call per coin per day (500 × M5 ≈ 41 h), plus a one-time deep H1 backfill. Cost is negligible; the value is that history exists from day one.
  • Subscribed series (demand from analysis): coin + timeframe pairs that are maintained live, derived and published.
  • Fetch frequency is driven by the shortest subscribed timeframe, not by the stored resolution.
  • Prefer one quote currency (USDT): prices, P&L and portfolio in one unit; IRT pairs mix coin moves with the rial's exchange rate.

4. Storage model

All tables belong to marketdata (analysis owns its own tables). Schema changes via Flyway.

CREATE TABLE candle (
    exchange     text        NOT NULL,
    symbol       text        NOT NULL,          -- e.g. 'BTC/USDT'
    timeframe    text        NOT NULL,          -- 'M5', 'H1', 'H4', ...
    open_time    timestamptz NOT NULL,
    open         numeric     NOT NULL,
    high         numeric     NOT NULL,
    low          numeric     NOT NULL,
    close        numeric     NOT NULL,
    volume       numeric     NOT NULL,
    source       text        NOT NULL,          -- 'REST' (native) | 'DERIVED'
    updated_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (exchange, symbol, timeframe, open_time)
);

CREATE TABLE market_series (                    -- facts ABOUT the data
    exchange          text NOT NULL,
    symbol            text NOT NULL,
    timeframe         text NOT NULL,
    kind              text NOT NULL,            -- COLLECTED | DERIVED
    status            text NOT NULL,            -- see section 6
    oldest_open_time  timestamptz,
    newest_open_time  timestamptz,
    published_until   timestamptz,              -- watermark: gap-free AND announced up to here
    history_complete  boolean NOT NULL DEFAULT false,   -- exchange answered no_data going back
    active            boolean NOT NULL DEFAULT true,
    updated_at        timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (exchange, symbol, timeframe)
);

CREATE TABLE market_job (                       -- work still to do ("scheduled" = a row here)
    id           bigserial PRIMARY KEY,
    type         text NOT NULL,                 -- FETCH_LATEST | DERIVE | BACKFILL_HISTORY | BACKFILL_RECENT | INITIAL_PAGE
    exchange     text NOT NULL,
    symbol       text NOT NULL,
    timeframe    text NOT NULL,
    range_from   timestamptz,
    range_to     timestamptz,
    cursor       timestamptz,                   -- resume point
    priority     text NOT NULL,                 -- LIVE > DERIVE > BACKFILL
    status       text NOT NULL,                 -- PENDING | RUNNING | DONE | FAILED
    attempts     int  NOT NULL DEFAULT 0,
    next_run_at  timestamptz NOT NULL DEFAULT now(),
    last_error   text,
    created_at   timestamptz NOT NULL DEFAULT now()
);
-- at most one OPEN job of a type per series -> scheduling twice is harmless
CREATE UNIQUE INDEX one_open_job ON market_job (type, exchange, symbol, timeframe)
    WHERE status IN ('PENDING', 'RUNNING');

CREATE TABLE series_subscription (              -- who needs which series (durable)
    subscriber_id  text NOT NULL,               -- e.g. 'analysis'
    exchange       text NOT NULL,
    symbol         text NOT NULL,
    timeframe      text NOT NULL,
    min_history    int  NOT NULL,               -- candles needed for warm-up
    created_at     timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (subscriber_id, exchange, symbol, timeframe)
);

Idempotent upsert

Re-fetching never duplicates; identical data is a no-op. If an already-published candle ever changes, it is detected and logged (correction events are deferred until they actually occur).

INSERT INTO candle AS c (exchange, symbol, timeframe, open_time, open, high, low, close, volume, source)
VALUES (...), (...)                                   -- batch de-duplicated by open_time in Java first
ON CONFLICT (exchange, symbol, timeframe, open_time) DO UPDATE
SET open = EXCLUDED.open, high = EXCLUDED.high, low = EXCLUDED.low,
    close = EXCLUDED.close, volume = EXCLUDED.volume, source = EXCLUDED.source, updated_at = now()
WHERE (c.open, c.high, c.low, c.close, c.volume)
      IS DISTINCT FROM (EXCLUDED.open, EXCLUDED.high, EXCLUDED.low, EXCLUDED.close, EXCLUDED.volume)
RETURNING c.open_time, (old.open_time IS NULL) AS inserted;   -- PostgreSQL 18: OLD/NEW in RETURNING

5. Scheduling: reconciler, jobs, worker

Terminology.

Scheduling = writing down work as a row in market_job. It is not a timer. Rows survive restarts and can be inspected with SQL.

Reconciler = a component that compares the desired state (collected universe + subscriptions) with the actual state (market_series) and schedules jobs for the difference. The term comes from control loops such as Kubernetes controllers: "observe → diff → act", repeated safely. It fetches nothing itself and is idempotent: running it twice creates no duplicate work.

Ticker = the only timer (Spring @Scheduled, every minute). It decides when live work exists.

Worker = the loop that executes jobs. The queue decides in what order; the throttled exchange client decides how fast.

5.1 Job types

JobPriorityCreated byDoes
FETCH_LATESTLIVE (highest)ticker, when a candle is duefetch from newest stored candle → now; store; derive; advance watermark; publish
INITIAL_PAGELIVEreconciler, new seriesfetch the newest page (500) to establish the head and give a warm-up window
DERIVEDERIVEreconciler / subscriptionbuild a derived timeframe over a range from stored base data (no API calls)
BACKFILL_RECENTBACKFILLreconciler, new coin or gap < 7 daysfetch base-resolution (M5) candles of the last 7 days
BACKFILL_HISTORYBACKFILL (lowest)reconciler, history not completewalk back from the oldest stored H1 to the start of the exchange's history

5.2 Reconciler (startup, config reload, new subscription)

reconcile():
  for coin in collectedUniverse:                          // desired: collection
      ensureSeries(coin, BASE, COLLECTED)                 // e.g. M5
      ensureSeries(coin, H1,   COLLECTED)                 // deep history
      if series has no head                    -> schedule(INITIAL_PAGE)
      if base gap within last 7 days           -> schedule(BACKFILL_RECENT)
      if !H1.history_complete                  -> schedule(BACKFILL_HISTORY, cursor = H1.oldest)

  for sub in subscriptions:                               // desired: demand
      s = ensureSeries(sub.coin, sub.timeframe, DERIVED)
      if s does not cover its source range     -> schedule(DERIVE)
      updateStatus(s)                                     // WARMING_UP / LIVE / STALE (section 6)

  for s in activeSeries not desired anymore:
      s.active = false                                    // stop work, keep data

schedule(type, ...):  INSERT INTO market_job ... ON CONFLICT DO NOTHING   // one open job per type+series

5.3 Ticker: is a candle due?

@Scheduled(fixedDelay = 60_000)             // fixed DELAY: runs never overlap
void tick() {
    for (series s : activeLiveRelevantSeries()) {
        Instant nextClose = s.newestOpenTime() + 2 * s.timeframe();   // the candle after the newest has closed
        if (nextClose + SAFETY_DELAY <= now())                        // e.g. 10 s after the close
            schedule(FETCH_LATEST, s, from = s.newestOpenTime());
    }
}

Due-based, not clock-based: it works for any timeframe and for exchange-specific boundaries (:30 UTC), and a series that missed a tick is simply still due on the next one. For a passively collected coin the same rule applies with a relaxed interval (≈ once per day).

5.4 Worker

loop (one per exchange, sharing that exchange's throttled client):
    job = SELECT * FROM market_job
          WHERE status = 'PENDING' AND next_run_at <= now()
          ORDER BY priority, created_at
          LIMIT 1 FOR UPDATE SKIP LOCKED
    mark RUNNING
    execute ONE chunk                      // one 500-candle page, or one derive block
    in the same transaction:
        upsert candles, update market_series, move cursor,
        advance watermark + record events (section 7)
    finished? -> DONE
    more?     -> PENDING                    // re-queued: LIVE work can run before the next chunk
    error?    -> attempts++, next_run_at = later, last_error; FAILED after N attempts

on startup: RUNNING jobs -> PENDING        // crash recovery, resume from cursor
  • One chunk per pick is what makes priorities work: a 140-page backfill never delays a fresh candle.
  • Backfill and live fetching never overlap: live extends the series forward from the newest candle, history extends it backward from the oldest.
  • SKIP LOCKED also allows several app instances later. Libraries such as db-scheduler or JobRunr implement the same idea; a single table + loop is enough to start.

6. Series lifecycle and statuses

LevelStatusesMeaning
Coin collection (base + deep H1)BACKFILLING → COLLECTINGis base data still being fetched?
Series (coin + timeframe)WARMING_UP → LIVE ⇄ STALE, INACTIVEmay a subscriber act on it?
              subscribe / new series
                       │
                       ▼
               ┌──────────────┐  enough history (≥ minHistory)  ┌────────┐
               │  WARMING_UP  │ ──────── AND caught up ───────► │  LIVE  │
               └──────────────┘                                 └───┬────┘
                                                 gap / falling behind│  ▲ caught up again
                                                                    ▼  │
                                                                ┌────────┐
                                                                │ STALE  │

     last subscriber unsubscribes (any state) ──► INACTIVE  (maintenance stops, data kept)
  • WARMING_UP: no events, no strategy evaluation. Reads are allowed (with coverage information).
  • LIVE requires both: at least the subscriber's minHistory gap-free candles and the newest stored candle is the latest closed one.
  • STALE: data fell behind or has a gap (exchange outage, our downtime). Strategy must not act until LIVE again.
  • Every status change is published as SeriesStatusChanged, so subscribers start, pause and resume without polling.

7. Consistency rules

  1. A series only grows at its two ends. FETCH_LATEST extends it forward from the newest stored candle (never "now minus something"); BACKFILL_HISTORY extends it backward from the oldest. The ranges are disjoint, so jobs can interleave freely.
  2. Only growth at the newest end publishes events. Backfilled history and bulk derivation never trigger analysis or strategy.
  3. Stored ≠ published. published_until is the watermark up to which the series is gap-free and announced. After every write, one "advance" step publishes the longest gap-free run after the watermark, in one event.
  4. The advance step is serialized per series (SELECT … FROM market_series … FOR UPDATE): watermark move, event record (outbox row later) and candle writes are one transaction, so nothing is announced twice.
  5. Derived candles follow the base watermark: an H1 candle is derived only when the base series' watermark has passed the end of that hour. A gap delays the derived candle instead of producing a wrong one.
  6. Corrections (a stored, published candle whose values change): detect and log only, for now. A CandlesCorrected event + recomputation in analysis is added only if it is seen in practice.
advance(series):                                   // under row lock on market_series
  run = longest gap-free run of stored candles starting at published_until + timeframe
  if run is empty:
      if stored candles exist beyond a gap -> schedule gap-fill FETCH_LATEST (LIVE priority); mark STALE if needed
      return
  published_until = run.last.openTime
  record CandlesClosed(series, run)                 // in-process publish now; outbox row later (Kafka)

8. Subscriptions and events

8.1 Contract between analysis and marketdata

// marketdata API (called by analysis; marketdata never calls analysis directly)
SeriesStatus subscribe(String subscriberId, Market market, Timeframe timeframe, int minHistory);
void         unsubscribe(String subscriberId, Market market, Timeframe timeframe);
List<Candle> getCandles(Market market, Timeframe timeframe, Instant from, Instant to);       // also derive-on-read
List<Candle> getLatestClosed(Market market, Timeframe timeframe, int count);

// events (through a publisher port: in-process now, Kafka + outbox later)
record SeriesStatusChanged(Market market, Timeframe timeframe, SeriesStatus status, Instant watermark) {}
record CandlesClosed(Market market, Timeframe timeframe, List<Candle> candles) {}   // ordered, gap-free, normally 1 candle
  • Subscribing is idempotent and stored durably; subscribers re-subscribe on every startup (a no-op if unchanged).
  • Events are sent only for series with at least one subscriber, and only while the series is LIVE.
  • A series is published once, however many subscribers it has (two strategies on BTC/USDT H1 share it).
  • One event per fetch: a catch-up of 30 candles arrives as one ordered batch, not 30 events. In normal operation the batch holds one candle.
  • Handover: the LIVE status event carries the watermark. The subscriber reads history up to it once; every CandlesClosed afterwards starts right after it. Nothing is missed or processed twice.
  • Coin collection continues regardless of subscriptions (it is driven by the collected universe).

8.2 Why events, and why not Kafka/Flink now

  • A second scheduler in analysis would duplicate marketdata's and add latency; marketdata already knows the moment a candle is stored.
  • Kafka/Flink are built for orders of magnitude more data and add infrastructure to run. Flink-style stream computation is not needed: ta4j computes our indicators directly.
  • Later, a Kafka publisher replaces the in-process one: candle writes and an outbox row are written in one transaction; a relay sends the outbox to Kafka (no dual-write problem). Keyed by market, events stay ordered per series.

9. Analysis and strategy

9.1 Analysis is stateless

  • On CandlesClosed: read the last ~500 candles from marketdata, compute indicators, store a feature snapshot per new candle.
  • No in-memory window, no warm-up/resync logic. Reading 500 rows once per hour is trivial.
  • Warm-up: recursive indicators (EMA, Wilder's RSI/ATR) need roughly 5–10× their period to converge, so the window is ~300–500 candles, not 14 and not 70,000. The longest indicator period defines minHistory in the subscription.
  • Results must be stored: auditability (what did the indicators say at decision time), charts (roadmap iteration 3), and strategy input.

9.2 Who determines the timeframe

The strategy. An indicator only has a period (EMA 20 = last 20 candles); the timeframe belongs to the series it runs on. A strategy declares market(s), timeframe(s) and indicators with parameters (multi-timeframe is possible, e.g. trend on H4, entry on H1). Analysis computes the union of what active strategies need and subscribes accordingly.

strategy  ──declares──►  (market, timeframe, indicators + parameters)
analysis  ──derives────►  per (market, timeframe): indicators to compute, minHistory ≈ 10 × longest period
analysis  ──subscribe──►  marketdata

9.3 Idempotency and freshness

  • Unique keys instead of "seen event" bookkeeping: feature snapshots keyed by (exchange, symbol, timeframe, open_time, indicator_config_version); proposals by (strategy, exchange, symbol, timeframe, open_time). A replayed or duplicated event becomes a no-op.
  • What must never duplicate is a side effect (a second BUY), hence the unique key on proposals.
  • Freshness rule: only the latest candle of a batch, and only if it closed within the last timeframe, reaches strategy. Catch-up candles update indicators/snapshots but never trade.
  • The config version in the key allows deliberate recomputation after a parameter change (EMA 20 → 21).

10. Sample flows

(a) Normal hourly close (BTC/USDT, H1 subscribed, base M5)

14:30:10  ticker: BTC base series due (hour 13:30–14:30 closed + 10 s)  -> FETCH_LATEST (LIVE)
14:30:11  worker: 1 REST call, M5 from newest stored -> 12 closed M5 candles
          tx: upsert M5 · derive H1 13:30 (skip v=0 fillers) · advance watermarks
              · record CandlesClosed(BTC/USDT, H1, [13:30])
14:30:11  analysis: read last 500 H1 -> EMA20/50, RSI14, ATR14, avg volume -> store snapshot
          candle is fresh -> strategy evaluates -> proposal (or nothing)

(b) App down for 4 hours → catch-up

restart   reconciler: nothing missing structurally; RUNNING jobs reset to PENDING
          series status STALE (behind) -> SeriesStatusChanged(STALE)
ticker    FETCH_LATEST from newest stored candle -> 48 M5 candles in one call
worker    derive 4 H1 candles; watermark advances by 4
          -> CandlesClosed(BTC/USDT, H1, [10:30, 11:30, 12:30, 13:30]); status LIVE
analysis  one computation, 4 snapshots; only 13:30 is fresh -> strategy;
          the 3 older candles never trade

(c) Analysis subscribes to ETH/USDT H4 (ETH not collected yet)

subscribe('analysis', ETH/USDT, H4, minHistory = 500)  -> status WARMING_UP
reconciler  ETH added to collection: INITIAL_PAGE, BACKFILL_RECENT (M5, 7 days), BACKFILL_HISTORY (H1, ~140 chunks)
            H4 series (DERIVED) -> DERIVE job (waits for source coverage, re-schedules itself)
worker      drains jobs in ~3 min, BTC's FETCH_LATEST still runs first every hour
            ETH H4 reaches 500 gap-free candles and is caught up
            -> SeriesStatusChanged(ETH/USDT, H4, LIVE, watermark = 2026-11-15T12:30Z)
analysis    reads history up to the watermark once, then follows CandlesClosed events
note        ETH M5 exists only from today (7 days back); deep history is native H1

(d) Duplicate or late event

CandlesClosed(BTC/USDT, H1, [13:30]) delivered twice (e.g. Kafka at-least-once, later)
analysis   INSERT snapshot ... ON CONFLICT DO NOTHING -> no-op
strategy   proposal key (strategy, BTC/USDT, H1, 13:30) already exists -> no second proposal
late event (hours old) -> candle not fresh -> never reaches strategy

(e) Gap → STALE → LIVE

exchange unreachable for 20 min; FETCH_LATEST fails, retried with back-off
series falls behind -> SeriesStatusChanged(STALE) -> strategy pauses on this series
exchange back -> FETCH_LATEST fetches the missing range -> watermark advances
-> one CandlesClosed batch + SeriesStatusChanged(LIVE)

11. Agents (future hooks, nothing built now)

Exploratory (agent, backtests, research)Operational (active strategies)
Needsany coin, any timeframe, deep historyspecific series, live, with events
Accessread-only queries, derive on read, no registrationsubscriptions → LIVE series → events
Side effectsnoneseries maintained while subscribed
  • Strategy discovery works on history, so the broad collected universe is what makes it possible (M5 cannot be recovered after 7 days).
  • Market scan: /market/stats returns 24 h statistics for all markets in one call (volume, change, best bid/ask).
  • Strategy definitions should be data (market, timeframe, indicators, parameters), so agent-proposed and hand-written strategies take the same path: backtest → shadow/paper → human approval → subscription → live. Agents propose; they never bypass risk or execution controls.
